开张半个多月，我把「改 markdown → commit → push → 等构建」这套站长寿数，升级成了一个网页后台。这篇记录接上它的思路，和第一轮全功能走查的收获。

## 为什么自己写一个

现成的方案（Decap、Sveltia 这类 git-based CMS）都很好，但登录这一步就卡住了：要么自建 OAuth 中转，要么手工管理 GitHub 令牌——对一个人用的后台来说都太重。干脆自己写：核心无非是「登录 + 读写仓库里的 markdown」。

## 它长什么样

![CMS 仪表盘：三张美西螈统计卡和最近文章列表](/assets/uploads/cms-dashboard-mvmssnnq.webp)

架构很简单：前台还是纯静态 Astro；后台是一个全中文单页应用；API 跑在边缘函数上，本地调试用 `node scripts/cms-dev.mjs` 就能起同一套环境。所有写操作都会变成一条中文提交信息进仓库，比如「CMS: 新增《标题》」，站点随后自动重新构建——发布延迟约一分钟。

安全上只守两条底线：GitHub 令牌只活在服务端环境变量里，浏览器永远接触不到；所有出站请求走白名单，只放行 api.github.com。

## 走查记：让最挑剔的用户来用

写完第一版，我以「第一次来的用户」的身份把每个功能点了一遍：错误密码的提示、连续输错的锁定、列表的搜索筛选、编辑器工具栏和撤销恢复、分屏预览换主题、草稿开关、图片拖拽粘贴上传、复制引用、删除确认……大部分顺滑，也抓到两个真问题：

1. **媒体库的事件监听会叠加**——每次进页面多挂一层，一次粘贴能触发重复上传，确认弹窗也会叠双层；
2. **编辑到一半离开页面没有任何保护**——误点一下侧栏，正文直接蒸发。

都是小代码病，好修。修完再来一轮。

## 一点感受

后台最难的不是堆功能，是敢把自己的真实体验当验收标准。这条走查路线，以后每次改版都跑一遍。
